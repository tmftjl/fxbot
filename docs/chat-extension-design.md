# 开放式 AI 对话扩展设计

状态：设计已落地。实际 API、hook 签名和使用约束见 [插件开发规范](plugin-development.md#开放式-ai-对话)。
本文保留设计目标与重构边界；实际用法以插件开发规范和行为测试为准。

## 1. 目标与原则

让插件既能控制一轮 AI 对话如何执行，也能控制何时开始对话、如何持续运行。
借鉴 AstrBot 的开放方式，复用 FxBot 自己的事件路由、Provider、工具、历史和发送实现，
不复制 AstrBot 的代码，不引入其完整 AgentRuntime / AgentSession 体系。

插件可以：

- 自选提示词和人格，也可以完全不用人格。
- 选择历史、插入或替换消息，自行使用长期记忆、表达、黑话和摘要。
- 选择 Provider、模型、温度和长度，一轮内允许更换 Provider。
- 提供动态工具，使用框架工具循环或自己编排循环及工具结果处理。
- 自定结束条件、最终回复、分段和进度消息。
- 优化默认门控，或接管调度、自建主动回复与心流。

基本原则：

- 插件是用户安装的可信 Python 代码，不把扩展上下文当作安全沙箱。
- 提供省事的标准执行路径，也开放底层服务，不强迫插件经过默认 Planner。
- 通过框架入口执行的操作遵守该入口的权限、guard、取消和历史契约。
- 插件绕过框架直接访问平台、数据库或执行函数，由插件自行承担一致性和生命周期责任。
- 不为防止插件写错而施加封闭的能力限制；必要的资源回收和执行状态仍由框架明确管理。
- 旧接口直接替换或删除，不保留兼容转发层；业务插件单独迁移，内置 server_admin、infinite_gen2 已完成适配。

## 2. 当前结构与问题

当前平台 AI 入口在 `src/fxbot/chat/router.py`，普通聊天经过防抖与门控后，
由 `behavior/turn_scheduler.py` 的 worker 调用 ChatService；Focus 使用自己的调度路径。
网页聊天和系统续话也会直接进入聊天服务，不一定有真实 Bot 或平台 Event。

主要限制：

- `system_prompt / prompt` 等 hook 主要追加文本，不能自由替换完整消息序列。
- 直聊生成路径不提供工具循环。
- 普通工具循环与回复生成绑定在 Planner 等核心实现中。
- Provider 租约、trace、历史准备和业务策略耦合，插件自行调用时容易重复实现。
- 默认门控可能在插件参与前就丢弃触发机会。
- `queue_message()` 会把后续消息交给活动 Planner，不能无条件用于插件自定义执行。
- 只新增 `_process_locked()` 内的 turn hook，不能解决入口之前的门控和 Focus 调度接管。

因此不采用最初的封闭式 `TurnContext / TurnResult` 控制器作为唯一扩展方式，
改为开放聊天服务、可修改请求与可替换调度。

## 3. 三层控制范围

| 层级 | 插件控制内容 | 框架自带实现 |
| --- | --- | --- |
| 触发门控 | 是否考虑回复、概率、冷却、防抖、活跃度 | 默认门控与回复节奏 |
| 对话调度 | 何时启动、等待、唤醒、合并、排队、打断 | 普通聊天调度与 Focus |
| 对话执行 | 提示词、消息、模型、工具循环、结束与回复 | 默认 Planner / 直聊 |

默认实现继续可用，但不是插件无法绕过的业务前置条件。
平台准入、基础权限拒绝、会话清空导致的轮次失效不属于可替换的回复概率策略。
当前 `can_reply()` 等检查中的基础开关与休息、节奏策略需按此语义拆清，不能直接整体绕过。

## 4. 上下文与请求对象

### HandlerContext：事件处理

保留事件、Bot、参数、处理器状态、应用服务、发送和 finish，新增动态停止传播。
不把模型、历史和心流业务塞进 BotClient。

### ChatContext：聊天能力

新增聊天执行上下文，暴露真实 ChatRequest、ToolRuntime 及正式聊天服务，
包括历史、人格、记忆、表达、Provider、工具、发送和结果提交。
插件可以修改工作对象，不限于不可变快照。

ChatContext 不继承 HandlerContext：网页聊天和系统续话没有完整的平台处理器上下文。
支持从 HandlerContext 创建，也支持核心从 ChatRequest + ToolRuntime 创建。

对象身份、Provider 租约和任务归属有明确生命周期；不建立一套用于隔离可信插件的能力沙箱。
后台工作使用独立任务及服务，不借用已经结束的响应器执行作用域。

### LLMRequest：模型请求

扩展现有 LLMRequest，作为可修改的请求工作对象，表达：

- 完整 messages，及可选的系统提示词、图片等输入。
- provider_id、model、temperature、max_tokens。
- 工具定义及对应执行注册表。
- 模型请求超时等生成选项。

显式传入完整 messages 时，不再偷偷注入默认人格、记忆、表达或 Planner 任务规则。
消息序列与独立系统字段并用时的拼接规则必须在最终接口中明确，避免重复注入。
现有 ChatRequest 仍描述入站消息与会话身份，不与 LLMRequest 混为一体。

## 5. 插件调用入口

| 入口 | 模型调用 | 工具循环 | 自动记聊天历史 | 自动发送 |
| --- | --- | --- | --- | --- |
| `llm_generate(request)` | 单次 | 否 | 否 | 否 |
| `tool_loop_agent(request, ...)` | 多次 | 是 | 否 | 否 |
| `request_llm(request)` | 核心执行 | 按请求执行 | 是 | 是 |
| 提交最终结果 | 不必调用 | 不必执行 | 是 | 是 |
| `send(message)` | 否 | 否 | 不作为最终 AI 回复记账 | 是 |

低层调用仍保留模型用量、调用追踪等必要运行记录；“不记聊天历史”不代表不记诊断信息。
提交最终结果让自行编排的插件也能复用核心持久化与发送，不必手写数据库操作。
同一次执行的用户条目、轮次开始和结果提交应可去重，避免多次产出重复记录用户消息。

### 交给核心执行

以下仅为建议调用形态：

```python
async def handle(ctx):
    ctx.stop_event()
    chat = await chat_service.context(ctx)
    request = LLMRequest(
        messages=[
            {"role": "system", "content": "只分析 bug 和编写代码"},
            *chat.history(),
            {"role": "user", "content": ctx.arguments},
        ],
        provider_id="coding",
        temperature=0.3,
        tools=my_tools,
    )
    await chat.request_llm(request)
```

### 自行编排

插件可以多次调用模型、切换 Provider、执行工具、重组工具结果、发送进度，
最后自行发送或提交最终结果。框架不禁止调用模型之后放弃处理，也不以返回 None 推断所有控制流。

模型调用、工具调用和循环步数提供可配置的默认超时或上限，
不写死全局 900 秒整轮限制，也不强制单 Provider。

## 6. 动态工具与标准工具循环

直接复用现有 ToolRegistry、ToolSpec、execute_tool() 和工具结果存储。
现有执行器已经接受指定 registry，不再创建第二套动态工具执行系统。

- 保留全局 `@tool`，允许插件建立本地 ToolRegistry。
- 支持选择、合并全局工具与当前请求的动态工具。
- 标准工具循环使用本轮指定的注册表，执行时复查权限和 tool_guard。
- 只有模型定义、没有执行处理器的工具可用于单次模型请求；自动工具循环需有明确执行映射。
- 复用参数校验、原始结果封装、序列化、截断与暂存。
- 工具结果整理是否额外调用模型应显式决定，不隐藏在普通序列化接口中。
- 不重复执行结果未知的有副作用工具，不因模型或插件失败自动重试整轮。

插件自己直接执行函数不受框架工具循环约束，也不承诺获得框架的权限检查和工具通知。

## 7. 新 hook 体系

继续复用注册、priority、稳定顺序与精确注销机制。
执行型 hook 接收可修改工作对象；停止、设置结果和替换执行方式使用明确操作，
不把“第一个非 None”作为唯一接管机制。

| hook 草案 | 职责 |
| --- | --- |
| `chat_request` | 修改本轮请求、选择执行策略，或处理后停止默认流程 |
| `llm_request` | 修改实际模型消息、Provider、参数和工具 |
| `llm_response` | 修改模型响应 |
| `tool_start / tool_end` | 参与工具调用与结果处理 |
| `reply` | 修改最终实际待发送内容 |
| `after_send` | 获取真实发送结果 |
| `chat_done` | 正常、失败、取消后的清理和统计 |

三种职责分开：

- 修改 hook：参与执行，不要求只读。
- guard：明确允许或拒绝，保留核心已有权限契约。
- observer：通知与诊断，不修改执行结果。

旧 persona / system_prompt / prompt / reply_text 可被新接口替代后删除，
不保留兼容别名。会话解析、会话策略和必要通知按职责保留或整理。

失败语义：修改型普通通知可参照 AstrBot 记录错误并继续；guard 失败仍拒绝。
真正承担本轮执行的插件处理器失败应结束该执行，不偷偷回落到普通聊天导致重复操作。
取消继续传播；最终实现需为每种 hook 明确错误策略，不使用一条宽泛异常规则覆盖全部入口。
模型 hook 应限定执行阶段，避免把回复提示注入摘要、学习或结果整理等辅助模型调用；
hook 自己调用模型也应能显式跳过同类 hook，避免递归。

## 8. 门控、主动回复与自建心流

### 默认门控之前观察消息

基础准入与权限检查后，插件应能在默认概率门控和调度选择之前观察消息。
默认不回复不等于插件没有收到消息。
对因基础权限拒绝而不可处理的数据，不通过此入口额外放行。
这里是消息观察，不是默认把全部消息写成 AI 轮次。

### 两种参与方式

1. 优化默认策略：读取消息和状态，修改触发判断，再交给现有调度器。
2. 替换调度：插件接管会话，维护自己的心流，默认普通调度和 Focus 不再同时启动回复。

每个会话、每个默认调度入口有明确的调度所有者。
多个插件对同一调度权的冲突必须显式仲裁，不能无声地各自发起默认回复。
这不禁止插件自行运行后台任务，而是防止框架默认调度重复执行。

### 调度服务需要开放

- 发起一轮对话或主动唤醒。
- 读取当前运行状态。
- 取消指定执行。
- 按执行器能力追加消息、排队或请求打断。
- 接收轮次结束和发送结果。
- 按应用与插件生命周期注销、取消和回收任务。

默认实现继续使用现有防抖、门控、普通调度及 Focus。
替换时清理或转交旧调度的待处理状态，并定义对已经运行轮次的处置，不能只切一个标志。
queue_message() 只向明确支持追加消息的执行器投递，不能把所有活动轮次都当成 Planner。

## 9. 长期记忆、表达学习与上下文增强

不删除这些能力，也不要求插件重写。

默认聊天维持当前人格、长期记忆、人物信息、表达、黑话、摘要和图片理解流程。
插件自定义流程有两种复用粒度：

- `prepare_request(...)`：按开关复用默认上下文组装，得到可修改的模型请求。
- 独立服务：按需获取记忆检索、表达参考、摘要、图片描述等结果，自行决定放入哪里。

示例形态：

```python
request = await chat.prepare_request(
    persona=True,
    memory=True,
    expressions=True,
    summary=True,
    vision=True,
)
request.messages.insert(1, {"role": "user", "content": "本轮额外参考"})
await chat.request_llm(request)
```

### 读取与学习写入分开

| 数据或能力 | 标准路径 | 自定义路径 |
| --- | --- | --- |
| 长期记忆、人物信息检索 | 按现有规则注入 | 按需使用 |
| 表达、黑话参考 | 按现有阶段使用 | 按需使用 |
| 真实用户消息 | 按现有规则记录 | 走标准入口时同样记录 |
| 实际发出的回复 | 成功发送后记账 | 提交最终结果时同样记账 |
| 记忆写回与表达学习 | 按现有配置触发 | 标准结果路径默认遵循同一配置，可显式关闭 |
| 系统提示词、内部规划、工具结果、临时参考 | 不当作普通用户发言学习 | 同样不因进入 messages 就自动成为学习材料 |

原则：模型看过什么，不等于系统应该学习什么。
学习来源与插件临时模型上下文分开，来源、实际发送结果和学习开关要可追踪。

## 10. 历史、发送与结果一致性

开放历史读取及正式追加、更新、清空服务，也允许高级插件使用现有底层服务。
标准路径仍保证：

- 模型 messages 的编辑不自动重写数据库历史。
- 用户消息、轮次开始和生成结果分别记账；执行失败有明确终态。
- 助手正文仅在实际发送成功后进入已发送可见历史。
- 分段部分成功时保留已发部分，未发部分不能伪装成已发送。
- reply hook 作用于实际发送内容，正文、分段和持久化来源保持明确。
- Provider 租约与 trace 在成功、失败和取消时正确释放或完成。

send() 用于进度和普通消息，不自动充当最终 AI 结果提交。
直接平台发送与核心最终回复发送分开说明，避免隐式重复发送。
metadata 可作为插件扩展数据使用，不把它当安全隔离边界；
核心调度、结果、发送状态优先采用明确字段，避免靠混杂魔法键驱动控制流。

## 11. 停止传播、取消与失效

| 操作 | 语义 |
| --- | --- |
| HandlerContext.stop_event() | 当前函数继续，返回后停止本响应器后续处理器及低优先级路由 |
| HandlerContext.finish() | 立即结束当前响应器，可先发送，不自动改变 block |
| 聊天执行停止默认处理 | 停止当前聊天 hook 链或默认策略，不等同于停止整个平台事件 |
| 取消指定聊天执行 | 请求终止指定模型/工具工作，传播取消并回收资源 |
| 清空会话 | 清理历史与调度状态，使旧轮次不再写回或发送 |

同优先级响应器并发，不因 stop_event() 取消同级已启动工作。
不通过修改 BotClient 增加传播控制，也不把路由的停止状态当成跨后台任务的万能取消令牌。
已经完成的外部工具副作用不能通过取消撤销。

## 12. ChatService 重构边界

从 ChatService 抽出统一执行骨架，复用而非复制已有实现：

```text
平台事件 → 基础准入 → 插件消息处理 / 调度选择
                         ├─ 默认防抖、门控、普通调度或 Focus
                         └─ 插件调度 / 自建心流
                                      ↓
统一聊天执行：准入、轮次锁、有效性、取消、trace
    → chat_request
    → 默认 Planner / 直聊 / 插件指定执行
    → 模型与工具能力
    → reply
    → 生成结果落库
    → 现有发送器与 send_guard
    → 成功发送记账、学习写回、after_send / chat_done
```

低层 llm_generate() 等服务不强行套上完整聊天记账；
需要标准历史、取消和发送保障时，使用托管聊天执行或结果提交入口。

## 14. 验收重点

- 默认普通聊天、直聊、Focus、控制台、系统续话继续正常运行。
- 插件可完整替换消息、人格、Provider、工具和结束逻辑。
- 单次模型调用不会自动执行工具，低层工具循环不会意外落库或发送。
- 动态工具执行经过所选注册表的处理器和现有权限、guard。
- 默认门控不触发时插件仍可观察、决定触发或自行调度。
- 同一会话不会因默认与插件调度重叠而产生两次框架回复。
- 新消息不会被错误并入插件流程的 Planner 队列。
- stop_event、finish、取消和清空互不混淆，状态不泄漏到其他事件。
- 发送失败和部分成功不污染可见历史；重复提交不会重复记录用户条目。
- 辅助模型请求不被回复 hook 意外改写，不出现模型 hook 递归调用。
- 临时提示、工具结果及内部规划不会被误当成真实用户消息学习。
- 插件失败、卸载、调度交接和应用关闭时，任务与 Provider 租约正确回收。
